# Construct evidence-led answer destinations

## Page-to-intent map
- Problem / informational → actionable guide with a decision tree and neutral options; link to offering only where genuinely suitable.
- Alternative / recommendation → transparent buying criteria, accurate matrix including non-fit cases, author disclosure and dated sources.
- Capability / requirements → feature documentation plus actual screenshots, configuration steps and limits.
- Free / cost → pricing page with what is truly free, restrictions, seat limits, add-ons, ongoing costs, policy/date.
- Integration → supported versions, permissions, screenshots, steps, import/export coverage and caveats.
- Managed service / consultancy → clear scope, industries, deliverables, process, verified service area, typical engagement model (not fictitious time or fees), case studies with permission.
- Security / privacy → substantiated architecture, permissions, storage location, policy and real compliance qualifications.
- Local and multilingual → genuine localized offer, clear contact/service coverage, language-correct copy, no translated doorway duplicates.
- ROI → assumptions, methodology, calculator and sensitivity ranges; no fake savings claims.

## Structure of a useful question-led page
1. H1 that expresses the task/problem rather than generic marketing slogan.
2. Immediate accurate answer in natural language: who can do it, under what constraints, and whether this product/service is a possible fit.
3. Concrete workflow or decision criteria; avoid rhetorical fluff.
4. Evidence (screenshot, steps, docs, observed comparison with dates).
5. Explicit limitations, unsupported cases, free/paid differences, risks.
6. FAQs representing **real distinct user needs** in the body, not 100 superficial paraphrases.
7. Related solution docs and relevant CTA.
8. Maintenance owner, date reviewed and changes log when features/terms change.

## Suggested schema (do not paste blindly)
Use truthful `Organization` for organization identity; `SoftwareApplication` for qualifying app pages; `Service` for service descriptions (schema.org vocabulary, not guaranteed Google rich result); `BreadcrumbList` where page navigation supports it. Schema must agree with on-page visible text and official provider documentation. Do not use FAQPage to chase Google FAQ rich results (no longer available there as of 2026).

## Publishing strategy
Publish **intent clusters** with unique demonstrable value. Do not create one URL for every word order or question. An exceptionally complete relevant page often supports multiple semantically adjacent questions. Maintain an internal content map: query -> one canonical page -> evidence -> conversion path -> evaluation prompt set.
